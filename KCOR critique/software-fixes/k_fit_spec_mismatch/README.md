# Candidate software/specification issue: baseline-rate fit

**Status: confirmed paper–implementation mismatch; the intended authoritative procedure is unresolved.** This is separate from the confirmed Monte Carlo sample-clock and diagnostic bugs in PR #4. No production code or manuscript source is changed here.

The retained manuscript says Step 1 jointly estimates the baseline scale \(k_d\) and an initial frailty parameter \(\theta_{0,d}^{(0)}\) by minimizing one objective over the nearest quiet window. [Retained manuscript source](<../../objections/1.3/objection3_resolution/source_snapshot/documentation/preprint/paper.md>) (section 2.4, Step 1).

The source used in the corrected objection 3 validation instead sets \(k\) to the average of the first four post-skip observed hazards divided by the assumed Gompertz growth factor. It then treats this value as fixed while fitting and iterating frailty and any offsets between quiet windows. The source docstring explicitly says “Direct k read” and “Hold k fixed.” [Frozen fitter source](<../../objections/1.3/objection3_corrected_validation/source_snapshot/code/KCOR.py>), function fit_theta0_gompertz. Its relevant lines are approximately 1141–1146, 1225–1238, and 1539–1550.

This is a substantive difference. Iterating frailty and offsets cannot revise a fixed \(k\). Under the exact expected counts of the model-consistent unequal-frailty scenario, the implemented fit returns a normalized value of 1.00461455 when the generating model's target is 1. Its fitted frailties are about 3.767 and 0.472 rather than 4 and 0.5. [Fit investigation](<../../objections/1.3/objection3_fit_investigation/FINDINGS.md>). A diagnostic joint fit under the production hazard approximation nearly removes the deterministic offset (0.99993565), but the estimates become more variable across sampled datasets. The separate exact conditional joint-fit pilot also has much wider intervals and noisier point estimates. Neither is a validated production replacement.

A separate [literal check of the paper's joint Step 1](<../../objections/1.3/objection3_paper_method/README.md>), using its continuous Gompertz objective on exact expected counts, gives 0.9999999663. This is evidence that the code's deterministic offset does not carry over to that paper step in the tested one-window scenario. It does not establish interval coverage for the manuscript's stated bootstrap.

**How to classify it:** If the paper's joint Step 1 is the intended algorithm, the current source has an implementation bug relative to the stated specification. If the direct early rate read is intentional, the manuscript's algorithm description needs correction and the consequences for the reported target and intervals need assessment. The evidence establishes the mismatch and its numerical consequence in the tested scenario; it does not establish which design the authors intended, that every KCOR output is affected, or that joint fitting should automatically replace the current method.

A resolution should first select the authoritative algorithm, identify which source revision generated any manuscript outputs being discussed, and then align implementation and documentation. A code change would require its own regression, saved-artifact replay, and fresh interval calibration. PR #4 should remain limited to its independent clock and diagnostic repairs.
